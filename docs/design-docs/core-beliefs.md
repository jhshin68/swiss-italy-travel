# DD-001: Core Beliefs — 핵심 신념

## 상태
✅ 확정

## 이 문서의 역할

에이전트가 판단이 애매할 때 돌아오는 최종 기준.
"이 기능을 넣을까?", "이 라이브러리를 쓸까?", "이걸 최적화해야 하나?" — 모든 질문의 답은 여기서 시작한다.

## 핵심 신념 5가지

### 1. 가족이 쓸 수 있어야 한다
```
"내 아내가 설명 없이 쓸 수 있는가?"
→ 이 질문을 통과 못 하면 기능을 단순화하거나 제거한다.
→ 기능의 풍부함보다 사용의 쉬움이 항상 우선.
```

### 2. 인터넷 없이도 쓸모 있어야 한다
```
"스위스 산 위에서, 이탈리아 기차 터널 안에서도 동작하는가?"
→ 핵심 기능(일정 열람, 경비 입력, 비상 정보)은 100% 오프라인 동작.
→ 온라인 전용 기능은 P1 이하로 분류.
```

### 3. 10월 여행 전에 완성해야 한다
```
"완벽한 앱보다 쓸 수 있는 앱이 낫다."
→ P0 기능을 9월 말까지 완성하는 것이 최우선.
→ 과도한 추상화, 미래 대비 설계는 상용화 단계로 미룬다.
→ TODO(COMMERCIAL) 주석으로 표기하고 넘어간다.
```

### 4. 데이터는 이미 있다
```
"처음부터 만들지 않는다. 기존 데이터를 활용한다."
→ itinerary.json (114개 일정), bookings.json (13건 예약), 
  checklist.json이 이미 준비되어 있다.
→ 앱은 이 데이터를 보여주고 관리하는 도구다.
→ 데이터 입력 UX보다 데이터 열람 UX에 더 투자한다.
```

### 5. 하네스 엔지니어링을 증명한다
```
"이 프로젝트는 AI 에이전트로 앱을 만드는 실험이기도 하다."
→ 설계 문서가 곧 코드의 설계도.
→ 문서 품질 = 코드 품질.
→ 이 경험이 향후 SL Power 내부 도구 개발의 선례가 된다.
```

## 충돌 시 우선순위

```
신념 충돌 시 번호가 낮을수록 우선:

1. 가족이 쓸 수 있어야 한다
   ↑ 최우선
2. 인터넷 없이도 쓸모 있어야 한다
3. 10월 여행 전에 완성해야 한다
4. 데이터는 이미 있다
5. 하네스 엔지니어링을 증명한다
   ↓ 후순위
```

예시: "오프라인 지도 캐싱을 구현하면 일정이 늦어질 수 있다"
→ 신념 3(일정) vs 신념 2(오프라인)
→ 신념 2가 우선 → 오프라인 지도 구현하되, 범위를 축소(핵심 지역만)
